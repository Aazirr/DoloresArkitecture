│  │  └─ [slug]/page.tsx         # Individual service (from MDX)
│  ├─ projects/
│  │  ├─ page.tsx                # Project gallery / showcase index
│  │  └─ [slug]/page.tsx         # Project detail w/ 3D viewer (from MDX)
│  ├─ blog/
│  │  ├─ page.tsx                # Blog index
│  │  └─ [slug]/page.tsx         # Blog post (from MDX)

## Conventions

- **Server vs client:** Components are Server Components unless they need browser APIs or
  interactivity. Anything under `components/three/` and `components/forms/` is client-side
  (`"use client"`). The 3D viewer is imported via `next/dynamic` with `ssr: false`.
- **Content stays in `content/`, code stays in `components/`/`lib/`.** Authors only touch
  `content/` (MDX) and `public/` (assets) — never the app code.
- **One MDX file per item.** Filename = URL slug (`villa-mactan.mdx` → `/projects/villa-mactan`).
- **3D models live in `public/models/`** and are referenced by frontmatter `model:` paths.
- **Shared Zod schemas in `lib/validation.ts`** so the contact form validates identically on
  client and server.
- **Path aliases:** `@/components`, `@/lib`, `@/content` via `tsconfig.json` `paths`.
- **Naming:** Components `PascalCase.tsx`; utilities/hooks `camelCase.ts`; MDX & routes
  `kebab-case`.

## Why this layout

- A flat, feature-obvious tree keeps a small team productive.
- Isolating `components/three/` makes the heavy WebGL bundle easy to code-split and reason about.
- Keeping `content/` separate from `app/` means content edits never risk breaking routing/logic.
